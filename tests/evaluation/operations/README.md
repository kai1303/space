# Channel and message latency

Run `pnpm test:performance` from the repository root. This builds the API, event bridge and MCP gateway and loads local test connection settings from `.env`. The default workload needs test PostgreSQL with logical replication and NATS. It starts an isolated API on loopback and cleans up the run's schema, replication slot, publication and streams.

The default is 20 waves with one sender. For four senders writing into the **same channel**, run `PERF_CONCURRENCY=4 pnpm test:performance`. Each wave starts all senders together. The channel begins with 100 messages. A separate authenticated member subscribes before measurement. HTTP and Socket.IO sends track both the sender response and the matching message appearing on that member’s socket. History requests fetch 50 messages. Channel management uses a fresh channel for each lifecycle. Signup, workspace creation, seeding and connection setup are outside the timed operations.

For the same workload across two API processes, run `PERF_API_INSTANCES=2 PERF_CONCURRENCY=4 pnpm test:performance`. Each sender uses the same API for HTTP and Socket.IO, with two senders per API. The receiver connects to the first API. Both APIs have their own connection pool and share the database, auth secret and event bridge. The report in `tests/test-results/operations/chat-4-2api/latency.json` records the API process IDs and participant assignments.

Single-API results are written to `tests/test-results/operations/chat-1/latency.json` or `chat-4/latency.json`. Each operation includes individual successful durations in milliseconds, nearest-rank p50 and p95, maximum, and count at or above 200 ms. Errors and incomplete scenarios fail the run. Sender acknowledgement and recipient delivery overlap. Timings do not include browser rendering or WAN transit.

## Broader suite

`PERF_SCOPE=all pnpm test:performance` also exercises authentication, user profiles, workspace operations and attachments. It requires an initialized SeaweedFS bucket, Typesense, ONLYOFFICE with access to that bucket, and the PDF thumbnail renderer. It creates isolated workspaces per scenario, uses a local email verification callback, and covers payloads up to the 25 MiB file limit. The broad suite observes the routes registered by the live API, including HEAD routes, and tracks the Space web client's auth flows individually. For Huddles, set LIVEKIT_URL, LIVEKIT_PUBLIC_URL, LIVEKIT_API_KEY and LIVEKIT_API_SECRET for a local development server. The suite creates and deletes its own rooms and invites only fixture users. Outbound discovery uses the real MCP gateway with a loopback protocol fixture. DNS and external TLS latency are outside that measurement. The Memory MCP workload uses the SDK and scoped tokens for the built-in Markdown provider. A missing provider-backed reply suggestion is recorded as a coverage failure. Use `PERF_OUTPUT` to set a different report directory and `PERF_ROUNDS` to change the sample count.

Set `PERF_METRIC=p95` to gate each operation on its nearest-rank P95. The default gates on the maximum. Both modes include raw samples, errors, incomplete workflows and missing routes. The broad workload runs independent workspaces on one API. For the shared-channel workload with eight senders, use `PERF_METRIC=p95 PERF_API_INSTANCES=2 PERF_CONCURRENCY=8 pnpm test:performance`.

Set `PERF_HEAD_ROUTES=1` with `PERF_SCOPE=all` for a separate HTTP HEAD coverage pass. Each workflow checks the registered HEAD route immediately after a successful GET on the same resource with the same credentials. It verifies status, routing and the empty response body, and records individual timings. The pass skips wildcard authentication links and checks GET responses with status 200 or 302. Its extra requests can affect enclosing workflow durations, so compare normal latency runs with this option disabled.
