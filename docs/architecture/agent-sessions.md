# Agent sessions

One Space thread can contain many agent sessions. An explicit Local Codex mention or accepted Navigator suggestion starts a managed session and its first turn atomically. A durable session reference is stored in the source thread. Channel and thread views render its link below the parent message using the same compact style as reply links, without a separate agent message row. Session references do not increase reply counts. Clicking a link opens the independent session panel; the reference survives completion, reloads and returning from the panel. Each explicit request starts an independent session. Ordinary discussion messages never start follow-up turns or inherit a previous agent owner's approval. Historical thread subscriptions are closed by migration033 and ignored by routing.

A session owns its conversation, progress and outputs. The thread discussion omits the old session creation bar, selection list, follow-up banner and Ask an agent controls. Saved agent replies do not gain Open agent session buttons. Back to thread returns to the source discussion; Close returns to the channel. The most recently opened thread's session view stays mounted while hidden so drafts and retry identities survive these transitions. Access revocation clears it. Follow-ups are sent through the selected session composer, which allows drafting while queued, working or awaiting approval but blocks sending until the current turn and refreshed state are ready. The session panel shares the thread header, virtualized message timeline, message renderer and rich composer. The composer follows the last message inside the scrolling conversation. Agent responses use the shared response renderer; requests retain rich-text documents. The header opens a separate right sidebar with Preview, Files and Changes. The sidebar omits the session summary and End session button. The conversation and composer stay mounted alongside it; narrow panels show the sidebar over the conversation. Close or Escape returns focus to the header button without losing the draft. Stop remains visible while a turn is active. Missing outputs have honest empty states; persistence does not enable repository or shell tools.

`agent_sessions` remains the storage identity. Migration030 adds title, active/ended state, creator, skill, managed flag and durable outputs. Existing sessions remain readable legacy runs. Each managed turn is an ordinary task with the same session_id, grants, owner approval, installation checks, execution receipts and outbox attempt fencing. Owners' messages autoapprove; other users' messages await the installation owner's approval. Idempotent retries preserve the same task; overlapping turns are rejected. Session event snapshots and replies stay inside the session and do not enter human thread history or Navigator.

## HTTP

- GET/POST `/v1/threads/:threadId/agent-sessions`: list or create using client_session_id, title and installation_id.
- GET `/v1/agent-sessions/:id?before=taskId`: latest20 chronological turns, an older cursor and durable session outputs independent of conversation pagination.
- POST `/v1/agent-sessions/:id/messages`: text up to4000 characters and an optional matching rich-text document; idempotency-key header required. Formatting is persisted with the task and participates in retry identity (migration035).
- POST `/v1/agent-sessions/:id/stop` or `/end`: creator/installation owner controls. End retains history and makes the session read-only.

Thread resource subscriptions refresh lists, conversation snapshots and outputs after committed changes. Access revocation clears the complete view. The session composer retains drafts and retry IDs while switching sessions/views.

Managed session mutations use serializable transactions and conditional revision updates. Migration031 adds the session revision; task revisions and execution sequences protect turn transitions. Database conflicts retry at most five transaction attempts, rechecking authorization and state each time; exhaustion returns409 session_conflict. These retries never repeat model inference. Session creation uses a unique client ID and ON CONFLICT rather than an advisory lock. Task delivery now uses committed WAL, JetStream push consumers and targeted deadlines. Attempt tokens fence stale results; they do not allow lease takeover. Other authoring and asset coordination gaps remain documented in principles.md.

## Codex persistence

Managed deliveries carry persistent_session.resume. The connector stores a private Codex home and Space-session-to-Codex-thread mapping under its own state directory, scoped by platform, workspace, installation, pairing and ChatGPT identity. It never imports desktop Codex history. First requests create non-ephemeral threads; later requests resume them. Mappings are committed before inference. An acknowledged session_ready progress marker coordinates backend/local readiness; a pre-turn stop can safely reuse an unused thread without replaying inference.

Stop/End return an intentional agent_session_stopped protocol result. The connector interrupts only that turn and waits for its acknowledgment/terminal event before claiming more work. Genuine transport/lease uncertainty still fails closed and never automatically repeats a model turn. Missing or mismatched retained history fails visibly instead of silently creating an empty conversation. Local history remains after connector restart and sign-out; it is available only with the same local installation and identity.

Response outputs are validated before persistence. Durable summaries retain the latest preview and latest20 file/change paths; preview documents use the existing sandboxed iframe. Local Codex and Kiro support opt-in project file tools through the local connector `--project` option; default launches remain chat-only. Tool activity and results reuse the response timeline, and typed activity appears above the shared composer. Other trusted output producers can attach files/previews/changes through the validated response envelope.

## Additional local providers

Kiro now uses the same managed-session lifecycle through ACP v3 and advertises persistent sessions. Provider selection, isolated authentication and validation limits are documented in [local agent providers](local-agent-providers.md).
